# 形式化模型与安全性分析节奏

## 1. 三类论文的组织差异

### 1.1 Tamarin 协议分析

P1 采用“协议概述 → 状态机/安全属性/攻击者模型 → 验证结果及分析”的顺序。安全属性在模型章中先定义，Dolev–Yao 攻击者随后说明；结果章再按保密性和认证性分组。P2 研究自动建模方法，采用“代码信息提取 → 通信状态机 → Tamarin 模型生成 → 实验”的流水线，威胁模型并非主轴。

共同特点是：

- 工具只介绍到读懂规则、事实、事件和验证结果所需的程度；
- 不在正文完整转录理论文件；
- 状态机、框架图或核心规则承担模型可读性；
- 结果表压缩多数性质，正文选择关键成功/失败解释。

### 1.2 ProVerif 协议设计论文

P4、P5、P6 都先完整说明系统/协议，再把 ProVerif 放入安全性验证。ProVerif 通常不是唯一证据，而是与 ROR 证明和非形式化攻击分析并列。工具部分简述进程、查询或四个场景，用一到数张终端结果图报告真假，再用短文解释机密性与认证含义。

这类论文不会把所有 ProVerif 进程和查询逐行放入正文。关键是说明查询对象、攻击场景和结果含义。

### 1.3 可证明安全协议

P3、P4、P5、P6、P7 的 ROR/BPR 证明遵循较稳定的顺序：

1. 定义参与者、会话、敌手查询和新鲜性；
2. 定义优势或安全事件；
3. 给出定理；
4. 用游戏序列或归约逐步给出上界；
5. 再补充攻击抵抗和性能比较。

这一高公式密度来自计算安全证明的研究对象。K-Waay 当前工作是有界符号语义比较，不应机械模仿 ROR 的定理—游戏篇幅。

## 2. 问题逐项回答

### 2.1 Threat Model 是否独立成章

没有样本把 Threat Model 设为独立一级章。4/7 有明确小节：P1“攻击者建模”、P3“敌手模型”、P5“威胁模型”、P6“攻击者模型”；其余把攻击能力嵌入 ROR 模型或方法说明。

因此 K-Waay 可保留威胁能力，但宜并入“2.1 安全目标与攻击者能力”，不需要维持英文稿的独立一级章。

### 2.2 Dolev–Yao 模型放在哪里

P1 将 Dolev–Yao 放在“形式化建模”末尾，位于状态机和安全属性之后。P5 在“协议设计”的网络模型之后设置“威胁模型”，同时写 DY 与 CK 能力。两者都把它靠近模型对象和安全目标，而不是在引言提前展开。

K-Waay 的批组成攻击者更适合在抽象入口处说明：先定义批内参与方目标，再列“保留、重放、选择、排列已暴露条目”的能力，并立即说明这是假定的组成边界能力，不是已证实的部署攻击面。

### 2.3 安全属性放在哪里

- Tamarin-MQTT：状态机之后、攻击者模型之前；
- PUF/认证论文：协议描述后，在安全性分析开头定义；
- BPR/ROR：安全模型中先定义实验和优势，协议之后证明；
- K-Waay：目标不变量应在形式化建模开头给出，具体 lemma 类别放在共同生命周期和事件之后。

这能形成“要证明什么 → 模型如何观察 → 具体性质如何编码 → 结果如何回答”的连续链。

### 2.4 模型规则列多少

样本只展示核心转换、状态机或代表性代码/规则。完整工具输入留给外部材料。P1 用状态机图和属性表；P2 用框架、状态机和代码片段；ProVerif 论文只解释必要进程/查询。

K-Waay 正文应说明：条目元组、两槽收集、三种准入谓词、精确源关系、五类事件/性质。无需逐条转录 Tamarin 规则或附录中的 14 个完整公式。

### 2.5 工具语法解释深度

稳定做法是“一段工具能力 + 一段本文映射”。读者需理解 multiset rewriting、持久事实、动作事实、存在/全迹性质和不等式限制；无需教程式介绍 Tamarin 所有语法。

K-Waay 可以用一张生命周期图和一张变体表完成大部分解释，正文只对 `Send`、`BatchReceive`、`ReceiverAccept`、`Reject`、`Neq` 的语义作定义。

### 2.6 攻击轨迹如何展示

P1 通过工具界面/轨迹与表格展示失败，并在正文解释攻击意义。认证论文的攻击分析更多用流程、场景和文字。样本不要求原始工具截图必须成为主要证据。

K-Waay 当前的重构轨迹图适合保留，但图题必须继续写明它是根据模型与执行记录重构的抽象轨迹，不是原始 prover 导出。正文应把时间顺序、坐标相等性和被反例推翻的性质说清楚。

### 2.7 验证结果的载体

7 篇均采用“图/表 + 文字”。Tamarin 论文由性质表和代表性轨迹支撑；ProVerif 论文由终端结果图和查询说明支撑；ROR 论文由编号公式/定理加性能表支撑。纯文字结果或逐性质长篇复述都不是主流。

### 2.8 是否把所有 lemma 放主表

P1 把大量性质分表汇总，但正文只解释关键项。K-Waay 的 14 条记录结果数量适中，可以完整放在一张紧凑主表中，以保证证据闭合；正文只围绕三条论证链解释：放宽反例、消息级非蕴含、参与方级安全与非空性。步骤数可移至脚注或附属材料，避免表格抢占语义重点。

### 2.9 模型限制写在哪里

样本通常没有独立 Limitations 章，而是在结果段或结束语局部限定。K-Waay 的证据边界比一般协议设计论文更敏感，完全省略会造成过度声称，因此推荐保留一个紧凑的“4.3 适用范围与局限”小节。它集中说明固定两槽、抽象接收事件、无完整密码过程、无部署/refinement 结论、基于既有执行记录。其他章节只在首次需要时各说明一次。

## 3. K-Waay 的建议节奏

1. 在协议问题章定义 BatchReceive 条件、身份坐标和最小问题实例；
2. 在形式化建模章首先定义参与方不变量和组成攻击者；
3. 用共同生命周期说明不变部分；
4. 将 relaxed/message-level/party-level 作为同一受控比较的三个变体，不包装成三套新协议；
5. 定义性质类别后立即进入结果；
6. 结果章按三个研究问题组织，并用一个汇总小节完成跨模型比较；
7. 讨论只保留语义非蕴含、设计责任和集中局限。

这一组织把 R/M/P 模型降到“回答研究问题的实验控制”，主线保持为“不同参与方条件维持什么语义关系”。
